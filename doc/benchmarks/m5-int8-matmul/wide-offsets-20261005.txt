Production change
Widen the native A/B/C pointer-offset products before multiplication, including
both complete- and partial-tile stores. No accumulator, quantizer, scalar IO,
selection, cache, attention, or backward changes.

At N_group_start=262144 and K=16384, the old uint multiplication evaluates
262144 * 16384 modulo 2^32 to zero. With N=262272, the last 128 output columns
therefore read the first 128 weight rows. B's INT8 payload is 4 GiB + 2 MiB.
The register path already uses size_t products; the native path now does too.

An opt-in regression allocates the actual large weight buffer, feeds the
production scaled-GEMM encoder, and compares 65 CPU-reference output samples
per case. Random nonzero and zero weight rows straddle the 4 GiB boundary.
Exact input quantization and power-of-two scales allow a bit-exact CPU
reference, including the FP16 store. M=511 covers a partial row tile as well as M=512's full tiles.
The test is separate from the default integration suite because it needs
approximately 4.3 GiB shared memory. It returns 77 if maxBufferLength is too small.

Before (unchanged baseline library):
  M=512 fixed:    PASS, 0/65 incorrect samples (register operands)
  M=512 dynamic: FAIL, 15/65 incorrect samples (native operands)
  M=511 fixed:   FAIL, 15/65 incorrect samples (native operands)
  M=511 dynamic: FAIL, 15/65 incorrect samples (native operands)
After: all four cases PASS, 260/260 samples exactly match the CPU reference.
For example, row 0 / column 262144 previously returned -0.817871 instead of
-5.10156. The fix restores -5.10156.

Unresolved selection issue
Dynamic M still returns false immediately in useRegisterOperands selection.
This retains the earlier "native for now" policy; it is not a limitation of
the runtime-M register shader. The address repair does not recover the Ultra
review's 64% / 30% partial-prefill gaps relative to ece05fbc.

A separate Max diagnostic prepopulates a one-shape pipeline cache with the
existing explicit register KernelDescriptor (loadM=true). It changes no
production source or quantization code. Each process uses only one M, so this
measures shader performance without making an unsafe cross-M reuse claim.
The same native/register/register/native protocol and CPU/output checks apply.

M x N x K                Native ms  Register ms  Reduction
512x2560x9216              0.404292     0.231396     42.77%
1024x4096x12288            1.274146     0.952937     25.21%

Both diagnostics produce bit-exact output hashes matching the native path.
They demonstrate recoverable throughput, not a production selection repair.

Why simply removing the loadM guard is insufficient
ShaderCache looks up NAInt8MatMulDescriptor before constructing the kernel
configuration. Its current dynamic equality treats all M<4096 as equivalent
for the same other execution facts. For N=2560/K=9216, M=511 and M=512 compare
equal, although the existing fixed-M selector chooses native and register
operands respectively on both 40- and 80-core profiles. Without changing that
equality, the first M to populate the cache would choose the path for both.

There are also narrower M-dependent selection boundaries. These are exact
host-selector results for an 80-core profile, NOT GPU measurements on Ultra:
  N=2176, K=8448: M512 register, M513 native, M577 register.
    M512: register grid 136 groups, native grid 68 groups; more cores reached.
    M513: register grid 153, native grid 85; native already reaches 80 cores,
          and register does not reach the 160-group admission threshold.
    M577: register grid 170; it reaches that threshold.
  N=2560, K=8192: M2457 native, M2458 register.
    The latter crosses M*N >= 4096*1536 with M >= 2048.
Thus one additional M512 boundary would not preserve all current decisions.
A subsequent selection change must make normalized equality/hash distinguish
M ranges where the selected configuration can differ. This can remain in the
existing descriptor; adding a separate PipelineCacheKey is not necessary.
The decision boundaries and cache reuse must be tested in both call orders.

Additional inherited lookup finding (unchanged)
The shared combine_32/combine_64 helpers in lib/nnc/mfa/ccv_nnc_mfa_hash.hpp
return a combined seed but do not
mutate their seed reference. NAInt8MatMulDescriptor's hash ignores those return
values, so the inspected hashes are all zero. Equality still distinguishes
keys and preserves correctness, but hashing does not distribute them. This is
separate from the M-range equality issue and the GPU timing gaps. It was not
changed here because the helpers and their callers are shared across MFA.
