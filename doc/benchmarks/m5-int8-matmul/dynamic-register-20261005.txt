NAInt8MatMul dynamic register selection, 2026-10-05
Branch: m5-na-int8-matmul
Baseline: 26fed9fc (native wide-offset repair)
Physical device: Apple M5 Max, 40 GPU cores, 128 GiB memory.

Dynamic M now uses the same kernel selection as fixed M. The blanket loadM
exclusion is removed. Descriptor equality and hashing share one normalizeM
helper, so cached selection is independent of the order in which M values
arrive. There are no new descriptor fields or PipelineCacheKey type.
KernelDescriptor retains the device-specific choices; the shader generator,
GPU-core gates, numerical precision, attention and backward code are unchanged.

How lookup normalization works
- Fixed M remains exact.
- Layouts/dimensions that cannot select register operands keep the two native
  traversal ranges: M below 4096 and M at/above 4096.
- For register-capable dimensions, M ranges preserve the relevant occupancy
  tile counts until the large-output criterion becomes true. That criterion
  is M >= max(2048, ceil(4096*1536/N)).
- Subsequent ranges preserve the native traversal boundary at 4096 and both
  M*K / M*N UINT32_MAX crossings used by selection.
- Actual M is still supplied to the shader and used for dispatch geometry.
  Only lookup comparison/hash are normalized.

Example with N=2560, K=9216, contiguous unbatched output:
  Actual M        Lookup representative
  1..511          0
  512             512
  513..576        513
  577..640        577
  ...             ... (same 64-row tile count)
  2433..2457      2433
  2458..4095      2458
  4096..466033    4096
  466034 onward  additional address-boundary ranges

The ranges are conservative across core counts. On a particular device,
several ranges can choose the same configuration. This may create more
pipeline entries than a device-specific key would, while source libraries
remain shared. Normal full 4096-token chunks retain fixed-M specialization.

The two NAInt8MatMul hash functions now assign the returned combine_32/64
values to their seed. Previously they returned zero for every key. The shared
MFA hash helpers and other operator hashes are unchanged. Optional stride
presence is distinguished in equality/hash, because explicit strides can
change source/constants even when their values equal the old nil sentinel.

Validation on Max
- make debug -j4 and the documented benchmark make targets passed. The
  dynamic_m_bench object needed an explicit rule to receive the MFA include
  paths and build flags; the make-built binary also ran the transition suite.
- 549,720 descriptor/configuration comparisons covered M=1..4352 plus address
  and signed-coordinate boundaries, 14 N/K pairs, and core profiles
  0/10/35/36/40/48/64/80/128. Equal dynamic keys always selected equal kernel
  configurations, and dynamic/fixed selection agreed.
- Actual pipeline-cache checks traversed four N/K pairs in both M orders on
  10/36/40/80-core policies. They verify reuse within ranges, source sharing
  across K specializations, and exact fixed-M keys.
- Existing 24 dynamic layout/reuse cases passed (batched/interleaved, bias,
  bit-exact fixed/dynamic outputs and independent CPU samples).
- New dynamic_m_bench mode 2 passed 88 cases using the actual 40-core policy
  and 88 more with an 80-core policy on Max. All fixed/dynamic outputs were
  bit-exact and the CPU samples passed. These check production encoding and
  cache reuse in both call orders. Mode 2 has no timing warmup, so its printed
  single-dispatch times are NOT performance evidence.
- The 80-core policy correctly selected register/native/register at
  M512/M513/M577 for N2176/K8448, and native/register at M2457/M2458 for
  N2560/K8192, regardless of call order.
- 18 direct register and 21 native configurations passed, including
  FP16/BF16/FP32, activation rotation, bias, strides and dynamic M.
- Four >4 GiB weight-buffer regressions and both focused BLAS tests passed.
- Production FP32, BF16 and FP16+H256 dynamic GEMMs at 513x2560x9216 passed
  CPU sample checks and matched their baseline full-output hashes.

No physical iPad or Ultra execution this round. The prior instruction to
