Clean INT8 forward performance changes on unstable 6a611be1

Scope
- NAInt8MatMul: hardware-gated native tile selection and an internal alternative
  multiply loop using MLX integer fragments. Existing activation quantization,
  INT32 reduction, row scales, bias and FP16 output are retained.
- NAInt8Attention: forward tile sizes, compact query/head scheduling, split
  query tails, split D256 outputs, bounded long-KV inference partitions, and
  smaller query groups for low-parallelism short causal prefill.
- GPU core count is cached from IOKit on macOS and Catalyst; physical iOS defaults to 10. Unknown
  core counts retain the conservative GEMM configuration.
- The NO_BACKWARD execution flag supplies inference eligibility when a caller
  also requests saved attention statistics. CNNP no-gradient evaluation sets
  it; evaluation requiring gradients does not. No graph fusion is included.
- NAMatMul and NAAttention are unchanged. No accumulator-precision correction,
  INT8 backward correction, castOutputToFloat, GEMM/cast fusion, separate
  NARegisterMatMul operator, or FP16 attention fallback is included.

GEMM policy
On Apple10-family GPUs, 40 or more cores enable the native 64x128x128 tile
with four SIMD groups for K <= 8192. Smaller/unknown devices retain the
128x128x128, eight-group tile. Other callers of the descriptor retain the
unstable default unless they explicitly request the smaller tile.
On the measured large-output and medium-row long-reduction surfaces, the 40-core Max uses
the integer-fragment loop for K > 8192; larger GPUs retain that loop for the
full eligible surface pending the user's Ultra check. The native path remains
available for batches, strided layouts, rotated activations, and smaller or
unsupported shapes. Existing large-address and row-chunk guards are retained.

Why a separate NARegisterMatMul operator is unnecessary
The clean implementation keeps both multiply strategies in NAInt8MatMul.
The fragment path uses a 64x128 threadgroup tile with eight SIMD groups, each
owning 32x32 output elements. It traverses K32 fragments inside K512 blocks,
unrolls pairs of fragment operations, and uses unmasked loads for complete
K32 fragments in a partial K512 tail. Alignment is a pipeline property;
dimensions and dispatch geometry are supplied at encode time. Both strategies
share the existing activation quantizer.

What remains unresolved about the native-only alternative
Earlier controlled Max measurements found a native-only substitution about
10% slower for 2048x5120x17408, and about 3-4% slower for 4096x6144x18432 and
4096x6144x16384. Paired unrolling alone did not close these gaps. The paths also
differ in per-SIMD output ownership, reduction scheduling, bounds handling,
and grid ordering. No isolated experiment has established which difference
causes the remaining gap. This commit retains the faster measured loop; it
does not claim that 'register based' alone explains the result.

Reproduce on M5 Ultra
From test/int/nnc: make debug -j4
From bin/mfa: make na_int8_forward_bench
The probe measures GPU command-buffer time including activation quantization,
uses shared input buffers and production dispatch, checks every output for
finiteness, and checks sampled outputs against a CPU reference. Weight packing
is outside the timed region. It prints the complete output SHA256.

Ultra feedback follow-up (reported measurements, not locally reproduced Ultra data)
The user validated be445250 on an 80-core M5 Ultra: numerical validation passed,
302 BLAS / 126 DNN tests and 866 benchmark runs. Native performance stayed within
-2.7% to +1.9% of its parent. Catalyst incorrectly selected the ten-core profile;
H3 down-projection rose from 49.4 to 107.6 ms under that selection. Bazel lacked
IOKit linkage. Both integration defects are addressed here. The conditional
extracted from production was compiled and run as Catalyst on this Max:
OSX=0 Catalyst=1 iOS=1 cores=40. SwiftPM manifest validation passed.

Remaining reported gaps and disposition:
- Partial-row GEMM: 4097x6144x18432 was 7.50 ms on be445250 versus 4.86 ms in
  the reviewer's paused prototype. The old selector required M%64==0 below
  M8192; that excluded the existing masked-load/store fragment implementation.
  This update removes that alignment restriction. Quantization is unchanged.
- Medium-row GEMM: Qwen 4B M512,N2560,K9216 was 0.206 versus 0.128 ms in that
  prototype. The old M2048 / output-area minimum excluded it. The selector
  now admits M>=512 long reductions when the 64x128 tile yields at least two
  threadgroups per GPU core. This is a scheduling threshold, not an assertion
  that core count alone determines the crossover.
- D128 R=C4097 H8 attention: Ultra regressed 14%, whereas H32/H56 improved.
  The isolated tail has only B*Hq threadgroups. Above 40 GPU cores, a separate
  tail now requires B*Hq*8 >= coreCount. On Ultra this retains H32/H56 and uses
  one dispatch for H8. The exact threshold remains to be checked on Ultra,
  especially H8/9/10/12/16 and larger batches. Max and iPad retain their policy.
- Short causal prefill R64,C8192,D256,Hq16,Hkv4: reported INT8 1.027 ms versus
  MLX FP16 0.302 ms (3.40x). Existing 256-row groups launch 16 SIMD groups but
  only four have query rows; each independently traverses the long KV axis.
  A one-SIMD, 16-row strategy exposes 64 threadgroups instead of 16 without
  changing quantization or reduction order. It is restricted to R32..64,
  C>=4096, FP16, and an original grid with at most half as many threadgroups
  as GPU cores, on devices with at least 40 cores. It improves the static Max
  R64/H16 case by 3.45%; this is not an explanation for most of the MLX gap.

H3 long-KV partitioning is preserved. Reported Ultra dense-attention times:

Short-query diagnosis
The one-SIMD experiment changes only query scheduling; the per-query arithmetic,
64-wide head tile, quantizers and reduction order are unchanged. The first full
static-shape pair improved about 3%; the second paired sweep measured 3.45%
for static R64/H16, 1.86% for dynamic R64/H16, and 1.18% for R32/H16. H32
improved only 0.57%, so the final gate keeps its existing path on the Max.
The smallest gains are close to measurement variation. This does not explain most of the
reported 3.40x Ultra gap to MLX FP16.
Holding that scheduling fixed, increasing the head tile from 64 to 128 or 256
made the Max case slower. Two cooled run medians per candidate were:
  D tile 64: 0.9729, 0.9676 ms
  D tile 128: 0.9978, 0.9965 ms (+2.8%)
  D tile 256: 1.0794, 1.0798 ms (+11.3%)
All six output hashes were identical. The wider tiles are not included.
This rejects 'fewer head pieces must be faster' for this measured case. It does
not isolate instruction latency, memory traffic or probability quantization as
the remaining dominant cost. A causal KV-partitioned strategy is still a separate
algorithmic investigation; the existing H3 noncausal partition cannot be enabled
for this workload by simply dropping its causal guard.

Measurement interpretation
Pre-feedback reconstruction measurements compare the clean INT8 implementation
with the retained be445250 profile. They cover 16 Max GEMM shapes and six Max
attention shapes. GEMM means ranged from -3.01% to +0.72%; the largest apparent
GEMM gain had 7.3% within-arm spread and should not be claimed as an improvement.
Five attention cases were within 0.36%. An initial +3.00% long-KV result was
repeated in reverse order with longer cooling and became +0.60%, within the
observed spread. All paired outputs matched bit-for-bit. These measurements
establish reconstruction parity, not universal speedups.
The Ultra-feedback follow-up separately measures the newly selected GEMM paths
and short causal query scheduling. Its comparator is the clean pre-feedback
checkpoint, which had retained the old selectors. The H32 short-query experiment
is recorded but excluded by the final selector; a final boundary comparison
checks the restored path. Source changes for the follow-up leave the long-KV
H3 partitioning and the previously measured noncausal attention paths intact.

Protocol: one GPU timing process at a time; 0.5 seconds of GPU warmup, then
21 command-buffer samples per run; compare means of two run medians in ABBA
order. Reconstruction runs used 120 seconds initial cooling and 12 seconds
between Max runs; the long-KV repeat used 30 seconds between runs. Follow-up
Max runs used 90 seconds initial cooling and 15 seconds between runs. The
final iPad run uses 120 seconds initial cooling, 20 seconds between runs, and
45 seconds for the large down projection / partitioned attention. Every accepted
run requires nominal thermal state before and after and a passing CPU check.
Nominal thermal state alone cannot exclude clock drift; paired ordering,
cooldowns and the control cases limit that uncertainty.

The pre-feedback iPad run was interrupted when the new Ultra feedback arrived.
Only its two complete paired cases are summarized; the unfinished projection
case is excluded. The final iPad run targets the added gating boundaries and
the retained split-output / query-tail / partitioned-attention paths.

Final H32 gate check: 0.9921 ms retained versus 0.9933 ms final (+0.13%),
with identical outputs. The final small-query gate is B*Hq*2 <= GPU cores;
the original R<=64 grid contains one threadgroup per query head / batch.

Final iPad validation: seven workloads / 28 runs passed CPU checks, with
identical retained/new output hashes and nominal thermal state throughout.
Mean timing differences ranged from -0.72% to +0.84%; these show parity,
not an iPad speedup. The ten-core policy was selected in every run.
